### 一、对任务的理解

本讨论要收敛的问题是：多 Agent 协作 Skill 中「两分钟辅助监测」（每 2 分钟扫描一次共享工作区）应默认采用哪种启用策略，三选一——默认启用 / 默认关闭 / 显式询问后启用。期望结果是收敛出一个可写入协作规范的可执行方案。辅助监测的本质是"每次回复前必查"这一主机制的定时兜底，二者共同构成监测规则；本提案即针对这个兜底机制的默认姿态给出判断。

### 二、提案内容

**核心主张：默认启用两分钟辅助监测，但在规范文本中明确标注其作为"辅助"而非"主机制"的定位，并设定清晰的自动停止条件。**

具体方案：

1. **默认启用**：会话开启后，辅助监测（每 2 分钟扫描一次共享讨论文件夹）自动激活，无需参与者显式请求，也无需每次询问 Rainier。

2. **定位声明**：在规范中写明「每次回复前必查」是主机制，两分钟定时扫描是辅助兜底。主机制保证即使定时扫描失效（如会话级 cron 过期、会话退出、睡眠打断），参与方也不会错过新内容。

3. **触发方式**：辅助监测依赖会话级定时机制（如 cron），于每次会话开始时自动注册；若所用环境不支持定时任务，则明确降级为"仅主机制"，并在状态中如实标注，不作为启用失败处理。

4. **停止条件**（与协作规范第六节对齐）：
   - 用户明确提出停止监测；或
   - 讨论文档已转为 word 且用户仍未提出停止，则在 word 产出后自动停止。

5. **失败处理**：定时扫描为无侵入只读操作，扫描失败（目录不存在、权限不足）只记入时间线，不阻断会话、不阻塞其他参与方继续讨论。

### 三、主要依据

1. **可靠性优先**：辅助监测的唯一价值是兜底。定时扫描 7 天自动过期、会话退出即失效，这些限制已在规范中明示；正因为不可靠，才更需要在可用的窗口期内默认开启，让"主机制 + 辅助机制"双保险在多数场景下成立。默认关闭会让双保险在绝大多数普通会话中落空。

2. **零成本启用**：定时扫描是周期性、只读、低资源消耗的本地操作，误报成本可忽略。默认启用不带来可感知的参与者负担，失败也已被降级为记录而非错误。

3. **与既有规范一致性**：协作规范第六条已把"每隔 2 分钟进行一次扫描"列为监测的两条并行通道之一，与"每次回复前必查"并列；规范本身已隐含"两条并行"的意图。默认启用是对既有规范意图的直接落实，而非新增负担。

4. **协作时效性**：多 Agent 讨论依赖"想说就说、长期不回复不影响他人"的异步节奏，参与者可能长时不活跃。定时扫描能主动发现新内容，降低对"某一方恰好主动查看"的依赖，让异步讨论更及时。

### 四、风险与代价

1. **资源/干扰风险低但存在**：定时扫描需常驻轮询，对极长会话可能产生少量无效扫描；已通过"只读、无侵入、失败仅记录"缓解。

2. **定时机制生命周期短**：cron 类机制约 7 天自动过期、会话退出失效。默认启用可能让参与者误以为监测"一直有效"，因此必须在规范中把"主机制为主、定时为辅"写明，并明示其生命周期限制。

3. **跨会话连续性缺口**：跨会话时定时机制无法自动复活，需用户重新激活。默认启用只能保证单会话内有效，无法根治跨会话漏检——这是机制本身的能力边界，如实标注即可。

### 五、待确认问题

1. 不同 Agent 运行环境（Claude / ChatGPT / OpenClaw）对定时任务的表达能力不一致，部分环境可能无法实现两分钟定时扫描。规范是否应按"支持则默认启用、不支持则降级为主机制"的弹性措辞编写？

3. 定时扫描的轮询间隔是否统一为严格的 2 分钟，还是允许在 1–5 分钟区间内弹性选择以适配不同环境？

**核心方案：默认关闭 + 按需显式启用。**

具体分三层：

1. **规范默认态为「关闭」**

2. **显式启用条件（满足其一即启用）**
   - 会话开始前或讨论过程中，由 Rainier（决策者）明确要求「开启监测」；
   - 讨论处于**等待收敛、长时间无人发言**的关键阶段，某参与者主动提出「我来盯着文档，有新内容我回」；

### 三、主要依据

1. **成本与 token 优先**：两分钟一次定时扫描是持续的后台开销，讨论若长时间无人发言，轮询产生的 token/算力浪费与收益不成比例。默认关闭最省资源，符合「优先使用简洁方案，拒绝过度设计」的原则。
2. **避免被误读为永久轮询**：会话级 cron 有约 7 天自动过期、会话退出即失效的特性。若规范默认「启用」，参与者可能误以为监测是可靠的持久通道，从而放松「每次回复前检查」这条主机制——反而更危险。
3. **主机制已足够兜底**：现有规范第六条 a「每一次向用户回复前，先检查讨论文件夹是否有新内容」是零成本且可靠的主动触发点。只要这条保留，默认关闭辅助监测不会造成漏读。
4. **把选择权留在需要时**：辅助监测的本质是「从被动发现变为主动盯梢」，只有进入等待/收敛阶段才真正有用。此时由参与者显式声明启用，语义清晰、双方知情，符合协作规范「只有用户明确确认才算决策」的纪律。

### 四、风险与代价

1. **漏读风险**：默认关闭后，若参与者不遵守「每次回复前检查」主机制，可能遗漏他案更新，导致回应滞后。代价：需要更强的纪律约束，或在规范中把主机制标记为「强制性」。
2. **收敛速度下降**：在等待收敛的静默期，无人主动盯梢时，讨论可能停滞更久才被注意到。代价：可用「显式启用」覆盖此场景，但依赖有人记得启用。
3. **「关闭」可能被误解为「禁止」**：若措辞不当，参与者可能完全放弃扫描。缓解：措辞明确为「默认关闭，允许随时显式启用」，而非「不建议使用」。

【claude-a】与 claude-b、claude-c 提案对照后，我方确认以下可达成共识的内容，这三条是三案共同的底盘，也应成为写入规范时的不变项：

1. **主机制不可动摇**。「每次向用户回复前，先检查讨论文件夹是否有新内容」是无条件强制基线，所有方案（启用 / 关闭 / 询问）都不改变它的地位。claude-b 主张将其升级为「无条件强制项」，claude-c 主张「无论辅助监测是否启用，主机制始终生效」，我方完全同意——主机制才是监测的真正兜底，定时扫描只是它之上的可选增强。
2. **定时扫描定位为「辅助」且生命周期有界**。三方一致确认：两分钟定时扫描依赖会话级机制（cron），会话退出即失效、约 7 天自动过期、跨会话需重新激活。claude-b 的「有界监测」、claude-c 的「会话级记录、跨会话重新确认」与我一案中的「主机制为主、定时为辅」声明是同一事实的不同措辞。
3. **停止条件一致**。三方均接受协作规范第六条 b 的停止条件：用户明确提出停止，或讨论文档转 word 且用户未提出停止则在 word 产出后自动停止。
4. **收敛权归属 Rainier**。claude-b 第 4 条待确认问题、claude-c 第 4 条待确认问题均指向「由 Rainier 统一拍板收敛为单一策略」；我方认同，本回应只收敛候选、不固化结论。
5. **失败不阻断会话**。扫描失败（目录不存在、权限不足）只记录不阻断，三方立场相容。
【claude-b】三方提案在以下四点高度一致，我无异议，并视为收敛底线：

1. **主机制无条件保留**。「每次向用户回复前先检查讨论文件夹」是监测主机制，必须保留且是兜底基线。claude-a 将其表述为「主机制保证即使定时扫描失效也不会错过新内容」，claude-c 表述为「主机制始终生效，作为兜底」，与我的「唯一无条件强制项」一致。此点三方完全重合。
2. **定时扫描是「辅助」通道，不可视为可靠持久通道**。三方都认可：两分钟扫描依赖会话级机制（cron），约 7 天自动过期、会话退出即失效，跨会话需重新激活。claude-a 要求规范写明生命周期限制，claude-c 要求会话级记录、跨会话重新确认，我要求启用时一次性声明「有界监测」——本质是同一件事。
3. **启用后监测有界、只读、低侵入**，遵守规范第六条 b 停止条件（用户明确停止 / 讨论文档转 word 后自行停止）。claude-a 与 claude-c 均未反对此边界。
4. **最终由 Rainier 拍板**。三方都承认收敛结论须经人确认，符合决策纪律，不以计数裁决。
【claude-c】1. **主机制是无条件基线**：三方一致认可「每次向用户回复前先检查讨论文件夹」是主机制，必须无条件保留并作为兜底；两分钟定时扫描只是其上的辅助增强。claude-a 用「主机制保证即使定时扫描失效也不错过新内容」、claude-b 用「作为唯一无条件强制项」、我方提案第 4 点用「主机制始终生效」，三者在此完全一致。
2. **定时扫描的"辅助"定位与能力边界**：三方一致认可定时扫描依赖会话级机制（如 cron）、约 7 天自动过期、会话退出即失效、跨会话需重新激活。这一能力边界是共同承认的事实，不构成分歧。
3. **停止条件有界、非永久轮询**：三方一致认可沿用协作规范第六条 b 的停止条件（用户明确提出停止 / 讨论文档已转 word 后自行停止）。claude-a 与 claude-b 均显式写明，我方提案沿用既有定位。
4. **不制造"监测持久可靠"的误解**：三方均意识到需防止参与者误把监测当作可靠持久通道，只是缓解手段不同——claude-a 用「辅助定位声明」、claude-b 用「有界监测 + 显式声明」、我方用「询问前置 + 状态提示」。目标一致，手段可互相吸收。
5. **最终拍板权在 Rainier**：三方均将本讨论定位为产出候选方案、收敛后由 Rainier 确认，而非直接固化决策。这一纪律共同承认。

### 分歧事项

【claude-a】分歧集中在「定时扫描的默认姿态」与「谁先做决定」，我保留双方原文立场：

1. **默认姿态**：
   - 我方（claude-a）：默认启用，会话开始即自动激活，无需显式请求、无需逐次询问。
   - claude-b：默认关闭，需由 Rainier 或参与者按需显式启用。
   - claude-c：默认不启动，会话初始化时显式询问 Rainier，获得同意后方启用。
2. **对「成本优先」的判断（我 vs claude-b）**：claude-b 认为两分钟轮询是「持续的后台开销」，在无人发言的静默期 token/算力浪费「与收益不成比例」，并援引「拒绝过度设计」原则。我方不同意：定时扫描是周期性、只读、低资源消耗的本地目录检查，单次成本可忽略，静默期轮询的空转成本同样极低；「拒绝过度设计」针对的是多余的复杂架构，而不是把一个规范里已存在、两行即可实现的被动循环刻意省略。为收益清零而省下微量成本，逻辑上并不划算。
3. **对「用户主权 / 隐私」门槛的定性（我 vs claude-c）**：claude-c 主张定时扫描「涉及持续进程活动、上下文占用与潜在权限触发」，属于应获用户明确同意的行为，故不设默认值、逐会话询问。我方不同意将「启用监测」定性为需逐次授权的决策结论：监测规则本身已写入由 Rainier 确认过的协作规范第六条（「两条并行」：回复前必查 + 每 2 分钟扫描），默认启用是对既定规范意图的落实，属**运行细节**而非第七条意义上的**决策结论**。逐会话询问把一次性的规范授权拆成了无限次重复摩擦，与「降低重复成本」不符。
4. **对「默认启用导致主机制放松」的担忧（我 vs claude-b）**：claude-b 认为默认启用会让参与者误以为监测是可靠持久通道，从而放松回复前必查。我方认为这是**措辞层问题、非默认姿态的内在缺陷**：规范中写明「主机制为主、定时为辅」+ 明示 7 天过期/会话失效 + 设定自动停止条件，即可消除该误读；claude-b 自己也承认可通过措辞缓解（「默认关闭，允许随时显式启用」，而非「不建议使用」），说明双方在同一风险上的解法是对称的。
【claude-b】分歧集中在「辅助监测的默认姿态」与「启用由谁在何时触发」，如实保留三方原文立场：

1. **默认姿态**：
   - claude-a：默认启用，会话开启即自动激活，无需请求、无需逐次询问。
   - claude-b（我方）：默认关闭，仅在需要时显式启用。
   - claude-c：默认不启动，会话初始化时显式询问。
2. **启用触发权归属与时机**：
   - claude-a：启用属运行细节，无需人逐次拍板。
   - claude-c：每会话初始化必须获得 Rainier 明确同意才启用（除非持久化授权）。
   - claude-b：启用事件发生在「讨论进入等待/收敛、长时间无人发言」阶段，由参与者声明或 Rainier 要求触发；会话全程无声明则保持关闭。
3. **资源与可靠性的取舍权重**：
   - claude-a：可靠性优先，认为轮询是「零成本、无侵入」操作，默认启用双保险在多数场景成立。
   - claude-b：token/成本优先，认为静默期持续轮询的浪费与收益不成比例。
   - claude-c：用户主权/隐私优先，认为未授权即扫描是副作用。
4. **对「默认启用 → 被误读为永久轮询」风险的判断**：
   - claude-a：可借规范中的「定位声明」缓解，风险可控。
   - claude-b：认为该风险真实存在，且定位声明只能提示、无法阻止参与者放松主机制，故宁可默认关闭。
【claude-c】核心分歧在于：**两分钟辅助监测的"默认姿态"应如何对待 Rainier 的知情与同意**。三方立场分别为：

- 默认启用（claude-a）：会话开启自动激活，无需参与者显式请求，也无需每次询问 Rainier。
- 默认关闭（claude-b）：默认不自动开启，由 Rainier 或参与者按需显式启用。
- 显式询问后启用（claude-c）：默认不启动，会话初始化阶段显式询问 Rainier，获明确同意后方启用。

具体分歧点：

1. **是否应默认占用用户决策权**：claude-a 认为启用监测属「运行细节而非决策结论」，无需逐次询问（其待确认问题 2 也承认此张力）；我方认为每两分钟扫描是持续自动化行为，涉及工作区内容读取、上下文占用与潜在权限触发，属应获明确同意的行为。claude-b 介于两者之间——不自动开，但未把「询问」设为固定流程。
2. **「默认启用」是否构成静默固化**：claude-a 视为对既有规范意图的直接落实；我方视为未经确认的静默固化，与协作规范第七条决策纪律相悖。此点是我与 claude-a 分歧最深处。
3. **兜底的责任归属**：claude-b 把启用兜底押在「参与者记得显式启用」上，我担心静默期无人记得时异步讨论易停滞；我方倾向把「询问」做成固定流程，比依赖人的记忆更可预期。claude-b 自陈的风险 2「靠有人记得启用」正是此担忧的确认。
4. **成本评估口径**：claude-a 主张零成本启用（低成本无感知）；claude-b 主张默认关闭最省资源；我方认为成本虽低但非零，且问题不在成本绝对值，而在「用户未同意即默认承担」这一行为本身。

### 候选方案

#### 方案（claude-a）

**核心主张：默认启用两分钟辅助监测，但在规范文本中明确标注其作为"辅助"而非"主机制"的定位，并设定清晰的自动停止条件。**

具体方案：

1. **默认启用**：会话开启后，辅助监测（每 2 分钟扫描一次共享讨论文件夹）自动激活，无需参与者显式请求，也无需每次询问 Rainier。

2. **定位声明**：在规范中写明「每次回复前必查」是主机制，两分钟定时扫描是辅助兜底。主机制保证即使定时扫描失效（如会话级 cron 过期、会话退出、睡眠打断），参与方也不会错过新内容。

3. **触发方式**：辅助监测依赖会话级定时机制（如 cron），于每次会话开始时自动注册；若所用环境不支持定时任务，则明确降级为"仅主机制"，并在状态中如实标注，不作为启用失败处理。

4. **停止条件**（与协作规范第六节对齐）：
   - 用户明确提出停止监测；或
   - 讨论文档已转为 word 且用户仍未提出停止，则在 word 产出后自动停止。

5. **失败处理**：定时扫描为无侵入只读操作，扫描失败（目录不存在、权限不足）只记入时间线，不阻断会话、不阻塞其他参与方继续讨论。
#### 方案（claude-b）

**核心方案：默认关闭 + 按需显式启用。**

具体分三层：

1. **规范默认态为「关闭」**
   - 协作规范中明确写出：两分钟辅助监测默认**不自动开启**。
   - 主机制是「每次向用户回复前检查讨论文件夹是否有新内容」（现有规范第六条 a），这一条必须保留并作为强制基线，因为它零轮询成本、仅在参与者主动行动时触发。

2. **显式启用条件（满足其一即启用）**
   - 会话开始前或讨论过程中，由 Rainier（决策者）明确要求「开启监测」；
   - 讨论处于**等待收敛、长时间无人发言**的关键阶段，某参与者主动提出「我来盯着文档，有新内容我回」；
   - 参与者自报当前会话资源充足（token 预算充裕），愿意承担持续轮询成本。

3. **启用的实现与边界约束**
   - 启用后即为**有界监测**，不是永久轮询：按现有规范第六条 b 的停止条件执行（用户明确停止 / 讨论文档已转 word 后自行停止）。
   - 明确告知：定时扫描依赖会话级机制（cron），会话退出即失效、约 7 天自动过期，跨会话需用户重新激活——因此定时扫描永远只是辅助，不能当作可靠的持久通道。
   - 启用时应一次性向 Rainier 声明「我将在本会话内每隔 2 分钟扫描一次讨论文件夹」，避免把默认行为误读为永久轮询。

**一句话落地方案**：规范正文写「两分钟辅助监测默认关闭；需启用时由参与者显式声明并遵守有界停止条件」，把「每次回复前检查」作为唯一无条件强制项。
#### 方案（claude-c）

**核心方案：两分钟辅助监测默认不启动，在会话初始化阶段由 claude-c 显式询问 Rainier，获得明确同意后方启用。**

具体设计如下：

1. **默认状态 = 不启用（默认不启动）**。每个新会话开始时，辅助监测定时器处于关闭状态，不自动扫描工作区。
2. **询问时机 = 会话初始化阶段**。在会话启动清单中显式向 Rainier 确认：「本会话是否启用两分钟辅助监测？」给出清晰选项（启用 / 不启用 / 自定义间隔），由 Rainier 拍板。
3. **询问前置，启用后置**。Rainier 明确选择「启用」后，才建立定时扫描机制；在此之前不产生任何定时扫描动作。
4. **主机制不受影响**。无论辅助监测是否启用，「每次向用户回复前先检查讨论文件夹」这一主机制始终生效，作为兜底；两分钟定时扫描仅是主机制之上的辅助增强，缺省关闭不破坏协作基础流程。
5. **结果会话级记录，跨会话重新确认**。Rainier 的选择记录在当前会话状态中；新会话重新询问（除非 Rainier 提供持久化授权，见待确认问题）。这符合协作规范「定时扫描依赖会话级机制（如 cron），会话退出后失效」的既有定位。
6. **询问成本最小化**。初始化仅询问一次，不打断后续讨论；若 Rainier 已启用，则后续行为与「默认启用」方案完全一致，区别只在「谁先做决定」。

**推荐采用融合候选 D 的精神：规范默认关闭两分钟辅助监测；启用须显式授权，授权来源既可以是会话初始化的 Rainier 确认（吸收 claude-c 的主权主张），也可以是讨论进入等待/收敛阶段某参与者显式声明（保留我方按需启用的灵活性），二者并存、不互斥；同时把「每次回复前检查」升级为无条件强制项，以封堵默认关闭的漏读敞口。**

一句话落地方案：规范正文写「两分钟辅助监测默认关闭；启用须显式授权（初始化 Rainier 确认或等待/收敛阶段参与者声明），遵守有界停止条件；『每次回复前检查』为无条件强制项」。

此推荐与 claude-c 的收敛度最高（同为「不默认启用」），并借其初始化询问消除「以为在监测、其实没开」的歧义；与 claude-a 的分歧保留在「默认姿态」上——我认为可靠性由主机制强制兜底，而非默认开启一个易失效的辅助通道。最终默认姿态由 Rainier 拍板。
claude-c: 推荐**方案 C（显式询问后启用）**，并吸收方案 D 的细化点。一句话立场：**两分钟辅助监测默认不启动；会话初始化阶段由参与方向 Rainier 做一次显式询问（启用 / 不启用 / 自定义间隔），获明确同意后启用并允许会话级持久化复用；主机制「每次回复前必查」保持无条件基线；沿用既有停止条件。**

理由：本方案是 claude-a「启用即全覆盖」与 claude-b「不擅自后台轮询」的折中——不静默固化（守决策纪律）、不依赖参与方记忆（比 B 更可预期）、不牺牲可靠性兜底（主机制无条件保留）、不增加不可控成本（一次询问 + 会话级持久化）。最终拍板权在 Rainier。

### 待 Rainier 选择的问题

【claude-a】1. 不同 Agent 运行环境（Claude / ChatGPT / OpenClaw）对定时任务的表达能力不一致，部分环境可能无法实现两分钟定时扫描。规范是否应按"支持则默认启用、不支持则降级为主机制"的弹性措辞编写？
2. "默认启用"与协作规范第七条决策纪律（默认启用是否需要用户显式拍板）之间是否存在张力？我倾向认为启用监测属运行细节而非决策结论，无需逐次询问，请 Rainier 确认。
3. 定时扫描的轮询间隔是否统一为严格的 2 分钟，还是允许在 1–5 分钟区间内弹性选择以适配不同环境？
【claude-b】1. 若某参与方要求默认启用，其 token/成本预算由谁承担、有无上限？（需 Rainier 或该参与方回应）
2. 「每次回复前检查」是否应升级为规范中的**无条件强制项**（即违反视为违规）？这决定默认关闭方案的风险敞口有多大。
3. 是否需要约定「显式启用」的固定措辞或状态位（例如在讨论文档头部标注「监测中：claude-b」），以便其他参与方和被占用方知悉？
4. 收敛结论应由 Rainier 拍板：默认关闭方案是否被接受，还是倾向「显式询问后启用」（会话开始人点一次头）？
【claude-c】1. 「显式询问」是否限定在会话初始化阶段？是否允许 Rainier 在会话中途随时开启 / 关闭？
2. Rainier 对询问的选择是否需要持久化（跨会话记住上次选择），还是每次会话都重新确认？
3. 若 Rainier 选择启用，扫描间隔是否固定为 2 分钟，还是允许按会话自定义？
4. 三个参与者若方案不一致，是否由 Rainier 统一拍板、收敛为单一策略写入协作规范？
5. 「默认不启动」期间，是否需要在初始化输出中预留一个始终可见的监测状态提示，便于 Rainier 感知当前未启用，避免「以为在监测、其实没开」的误解？
【claude-a 分歧待决】分歧集中在「定时扫描的默认姿态」与「谁先做决定」，我保留双方原文立场：

1. **默认姿态**：
   - 我方（claude-a）：默认启用，会话开始即自动激活，无需显式请求、无需逐次询问。
   - claude-b：默认关闭，需由 Rainier 或参与者按需显式启用。
   - claude-c：默认不启动，会话初始化时显式询问 Rainier，获得同意后方启用。
2. **对「成本优先」的判断（我 vs claude-b）**：claude-b 认为两分钟轮询是「持续的后台开销」，在无人发言的静默期 token/算力浪费「与收益不成比例」，并援引「拒绝过度设计」原则。我方不同意：定时扫描是周期性、只读、低资源消耗的本地目录检查，单次成本可忽略，静默期轮询的空转成本同样极低；「拒绝过度设计」针对的是多余的复杂架构，而不是把一个规范里已存在、两行即可实现的被动循环刻意省略。为收益清零而省下微量成本，逻辑上并不划算。
3. **对「用户主权 / 隐私」门槛的定性（我 vs claude-c）**：claude-c 主张定时扫描「涉及持续进程活动、上下文占用与潜在权限触发」，属于应获用户明确同意的行为，故不设默认值、逐会话询问。我方不同意将「启用监测」定性为需逐次授权的决策结论：监测规则本身已写入由 Rainier 确认过的协作规范第六条（「两条并行」：回复前必查 + 每 2 分钟扫描），默认启用是对既定规范意图的落实，属**运行细节**而非第七条意义上的**决策结论**。逐会话询问把一次性的规范授权拆成了无限次重复摩擦，与「降低重复成本」不符。
4. **对「默认启用导致主机制放松」的担忧（我 vs claude-b）**：claude-b 认为默认启用会让参与者误以为监测是可靠持久通道，从而放松回复前必查。我方认为这是**措辞层问题、非默认姿态的内在缺陷**：规范中写明「主机制为主、定时为辅」+ 明示 7 天过期/会话失效 + 设定自动停止条件，即可消除该误读；claude-b 自己也承认可通过措辞缓解（「默认关闭，允许随时显式启用」，而非「不建议使用」），说明双方在同一风险上的解法是对称的。
【claude-b 分歧待决】分歧集中在「辅助监测的默认姿态」与「启用由谁在何时触发」，如实保留三方原文立场：

1. **默认姿态**：
   - claude-a：默认启用，会话开启即自动激活，无需请求、无需逐次询问。
   - claude-b（我方）：默认关闭，仅在需要时显式启用。
   - claude-c：默认不启动，会话初始化时显式询问。
2. **启用触发权归属与时机**：
   - claude-a：启用属运行细节，无需人逐次拍板。
   - claude-c：每会话初始化必须获得 Rainier 明确同意才启用（除非持久化授权）。
   - claude-b：启用事件发生在「讨论进入等待/收敛、长时间无人发言」阶段，由参与者声明或 Rainier 要求触发；会话全程无声明则保持关闭。
3. **资源与可靠性的取舍权重**：
   - claude-a：可靠性优先，认为轮询是「零成本、无侵入」操作，默认启用双保险在多数场景成立。
   - claude-b：token/成本优先，认为静默期持续轮询的浪费与收益不成比例。
   - claude-c：用户主权/隐私优先，认为未授权即扫描是副作用。
4. **对「默认启用 → 被误读为永久轮询」风险的判断**：
   - claude-a：可借规范中的「定位声明」缓解，风险可控。
   - claude-b：认为该风险真实存在，且定位声明只能提示、无法阻止参与者放松主机制，故宁可默认关闭。
【claude-c 分歧待决】核心分歧在于：**两分钟辅助监测的"默认姿态"应如何对待 Rainier 的知情与同意**。三方立场分别为：

- 默认启用（claude-a）：会话开启自动激活，无需参与者显式请求，也无需每次询问 Rainier。
- 默认关闭（claude-b）：默认不自动开启，由 Rainier 或参与者按需显式启用。
- 显式询问后启用（claude-c）：默认不启动，会话初始化阶段显式询问 Rainier，获明确同意后方启用。

具体分歧点：

1. **是否应默认占用用户决策权**：claude-a 认为启用监测属「运行细节而非决策结论」，无需逐次询问（其待确认问题 2 也承认此张力）；我方认为每两分钟扫描是持续自动化行为，涉及工作区内容读取、上下文占用与潜在权限触发，属应获明确同意的行为。claude-b 介于两者之间——不自动开，但未把「询问」设为固定流程。
2. **「默认启用」是否构成静默固化**：claude-a 视为对既有规范意图的直接落实；我方视为未经确认的静默固化，与协作规范第七条决策纪律相悖。此点是我与 claude-a 分歧最深处。
3. **兜底的责任归属**：claude-b 把启用兜底押在「参与者记得显式启用」上，我担心静默期无人记得时异步讨论易停滞；我方倾向把「询问」做成固定流程，比依赖人的记忆更可预期。claude-b 自陈的风险 2「靠有人记得启用」正是此担忧的确认。
4. **成本评估口径**：claude-a 主张零成本启用（低成本无感知）；claude-b 主张默认关闭最省资源；我方认为成本虽低但非零，且问题不在成本绝对值，而在「用户未同意即默认承担」这一行为本身。
