# 多 Agent 协作规范

## 概述

本规范定义「人 + 三个独立 AI agent（Claude / ChatGPT / OpenClaw）协作模式」的通用规则，适用于任何需要多方 Agent 共同讨论并收敛结论的场景。核心特征：同一文档讨论、独立提案、文件占用感知、文档监测、人工拍板。

## 一、角色定义

- **决策者（人）**：决定何时收敛结论；指定文档创建者；参与方意见不一致时由人最终拍板。
- **三个 AI agent（Claude / ChatGPT / OpenClaw）**：地位平等，各自独立提案与评审，互不替代。

## 二、协作媒介与文档规范

1. 每个讨论子项目建立一个主讨论文档。
2. 文档命名必须为：`当前讨论子项目名称 + 讨论文档`，建议带日期（如 `证据类型讨论文档_2026-08-01.md`）。
3. 主讨论在同一文档内进行；辅助文档（评审稿等）允许存在，但须标注"辅助输入，非讨论主文档"。
4. 文档创建者由人指定；若创建者无 word 转换能力，由具备文件读写能力的参与方代执行转换，或由人指定。

## 三、讨论流程

1. 四阶段：独立提案 → 交叉回应 → 收敛候选结论 → 人确认转正式决策。
2. 不强制规定讨论顺序和讨论人次，想说就说，顺序无所谓。
3. 长期不回复的参与方不影响其他 agent 继续讨论。
4. 每轮记录时间线（谁在何时加了什么），供审计。

## 四、独立提案纪律

1. 首次在文档内提出提案时，不允许查看其他 Agent 的提案。
2. 必须先独立思考并给出自己的提案，之后才查看其他 Agent 提案并给出回应。

## 五、文档占用与并发

1. 占用定义：某 Agent 正在编辑文档时，其他 Agent 无法编辑（文件被占用 / 写入失败），即为"被占用"。
2. 被占用时：优先等待其他 Agent 编辑完成后再查看 / 编辑。
3. 等待超时：编写到独立文档，下次轮到该 Agent 时合并回主文档，或由其他 Agent 合并过去。
4. 并发冲突：若同时编辑，按提案顺序解决——即首次编辑文档的先后顺序。

## 六、监测与激活规则

1. 文件传感器只负责观察，不能代替流程推进。参与者若启用自动协作，应运行自己的 `participant_monitor.py`，以 Event Stream 为输入、以 cursor 为恢复点，并按 event_id 幂等消费与自己相关的事件。
2. Monitor 发现事件后由 Activation Bridge 尝试继续已有会话；结果必须明确为 `activated`、`manual_activation_required` 或 `activation_failed`。没有 dispatcher 时不能把扫描或聊天消息写成成功唤醒。
3. 协调者仍负责门禁、阶段转换和语义收敛；参与者 Monitor 不得修改 `state.json`、主讨论文档或替代 Coordinator。每个 Agent 的业务动作必须通过自身 Runtime 写入白名单产物和回执。
4. 定时机制（如 cron）是运行方式，不是协议事实源。会话退出或任务过期后，Monitor 必须能从 cursor 恢复；事件流、cursor 或事务日志无法验证时 fail-closed。停止条件由正式决策后的 `stop_requested` 和有效 stop 回执决定；候选 Word 审阅期间不得提前停止。

## 七、决策纪律

1. 只有用户明确确认的事项才标记为"已确认决策"；提案、建议、待讨论内容必须清楚标注，不得静默固化为结论。
2. 收敛结论由用户决定何时达成。
3. 参与方意见不一致时，收敛为候选结论，由用户最终拍板。

## 八、产出规范

1. 所有参与方结论收敛后，由文档创建者（或人指定的参与方）将文档转为 word 供人查看。
2. word 转换使用脚本：`scripts/export_docx.py`（python-docx，中文字体微软雅黑）。
